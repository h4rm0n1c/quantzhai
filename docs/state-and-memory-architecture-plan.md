# State and Memory Architecture Plan

Date: 2026-05-12

Status: planning document. Do not implement database code before the scope model,
storage roles, privacy boundaries, and migration path are grounded in real repo
metadata and capture evidence.

Review status: DeepSeek's repo review confirmed the direction is sound, but
found that several key scope identifiers are not currently available in
QuantZhai. This plan now treats those identifiers as prerequisites, not assumed
facts.

QuantZhai does not only need a stateful runtime store. It needs a **typed memory
architecture**: different kinds of state/memory serving different roles, with
explicit scopes, promotion rules, retention policy, and leak barriers.

A database is only the substrate. The important design question is:

```text
What kind of memory is this, who may read it, how long does it live, and what
can it influence?
```

---

## 1. Why this exists

The repeated-read signal revealed a concrete gap:

```text
Manual-history path:
  Codex/local client sends prior items in body["input"].
  The proxy can reconstruct recent tool/file history from the request.

Stateful previous_response_id path:
  Client may send only incremental input plus previous_response_id.
  Server/proxy must resolve prior history.

Compaction path:
  Older messages, tool calls, tool results, and reasoning may be replaced by a
  compacted item. Prior function_call items may no longer be visible.
```

That makes repeated-read v1 possible with visible request history, but repeated-
read v2 and future convergence signals require durable state.

However, this is larger than repeated reads. QuantZhai also needs long-lived
state for:

```text
runtime truth
response chains
session identity
workspace facts
coding-agent skills/preferences
profile-private memory
roleplay/private isolation
HSM / Holstrom archive integration boundaries
telemetry and debugging
compaction-aware structured facts
```

Those are not the same kind of memory. Treating them as one global bag of facts
would be dangerous and wrong.

---

## 2. Core principle

```text
Every persisted fact must have a type, a scope, a retention policy, and an
allowed influence surface.
```

If that cannot be answered, the fact should not be persisted yet.

The database should answer:

```text
What happened?
Where did it happen?
Which profile/session/workspace did it belong to?
Who may use it later?
Can it influence model behaviour, or is it only diagnostic?
Can it be promoted to a wider scope?
Can it be exported to HSM/Holstrom work?
When should it expire?
```

Default rule:

```text
No cross-scope read unless a policy explicitly allows it.
```

## 3. Current repo grounding

This section records what is known today from the repo review. Do not design the
first DB layer as if unavailable fields already exist.

### 3.1 Scope metadata currently available

```text
Available / reliable:
  request_id generated by QuantZhai
  selected profile/model slug
  backend model id
  prompt policy metadata
  turn harness metadata
  reasoning policy metadata
  generated local response ids

Not available / not consumed today:
  client session_id
  client thread_id
  previous_response_id as a resolved server-side chain
  client cwd / git root / repo URL
  workspace_id
  explicit profile_family
```

Important distinction:

```text
QZ_ROOT is QuantZhai's own repo root. It is not the client's coding workspace.
```

### 3.2 Current JSON/file ownership

Current file roles from the repo review:

```text
var/model-state.json
  State fallback for selected model. Live truth is in-memory ModelRouter.

var/backend-state.json
  State fallback for backend state. Live truth is in-memory ModelRouter.

var/run/qz-runtime-state.json
  Startup/debug snapshot. Not normal proxy live truth.

var/model-inventory.json
  Generated model scan cache/inventory. Deferred from DB migration until catalog
  ownership is fully settled.

var/codex-home/config.toml
var/codex-home/model-catalogs/*.json
  Generated Codex-facing files. Keep file-based because Codex consumes files.

var/codex-home/sqlite/*
  Codex's own internal state. Do not treat as QuantZhai-owned DB state.

var/captures/*
var/logs/*
var/benchmarks/*
  Debug/replay/artifact files. Not model memory by default.

config/default/*.json
config/example/*.json
config/user/*.json
  Human-editable or copyable config. Keep file-based.
```

### 3.3 Consequence for Phase 1

The first persistence patch must not pretend to have full scoped memory. It can
store request/response/tool/signal facts only where identity is known or
proxy-owned.

If real Codex traffic does not provide session/thread identifiers, Phase 1 must
use proxy-owned generated session identity and label it as such.

If `profile_family` and `workspace_id` are not grounded, cross-profile and
cross-workspace memory queries must remain disabled or limited to explicitly
known scope.

## 4. Memory classes

```text
Proxy/backend/process truth.
```

Examples:

```text
active model/profile
backend context size
request ids
response ids
backend load state
restart-required flags
```

Current repo state:

```text
Runtime truth currently lives mostly in in-memory ModelRouter / TelemetryBus,
with JSON files acting as fallback or startup/debug snapshots.
```

Allowed readers:

```text
proxy internals
/qz/status
qz-top
qz-thoughts
qz-doctor
```

Default model influence:

```text
None, unless deliberately surfaced as a runtime/status signal.
```

Storage direction:

```text
SQLite live truth later; optional JSON compatibility exports.
```

---

### 4.2 Operational tool memory

Purpose:

```text
Make agents converge better during tool use.
```

Examples:

```text
file reads
file writes
repeated-read warnings
repeated directory probes
tool-call counts
backend-error vs task-error provenance
search quality observations
compaction boundaries
```

Current repo state:

```text
Not implemented yet. repeated-read v1 remains stateless and input-history
seeded. Do not block v1 on the DB architecture.
```

Allowed readers:

```text
same session/workspace/profile-family when those scopes are grounded
```

Default model influence:

```text
Allowed as small advisory signals inside the same permitted scope.
```

Storage direction:

```text
SQLite structured facts for v2+, not full transcripts by default.
```

---

### 4.3 Conversation/session memory

Purpose:

```text
Remember what happened inside one conversation/session or response chain.
```

Examples:

```text
response chain
function_call/function_call_output metadata
compaction events
session-local warnings
session-local decisions
```

Current repo state:

```text
No durable session/response-chain memory exists today. request_id and local
response ids are generated, but not persisted into a chain store.
```

Allowed readers:

```text
same session/response chain by default, once session identity is grounded
```

Default model influence:

```text
Allowed only inside the same session/chain unless explicitly promoted.
```

Storage direction:

```text
SQLite metadata and structured facts. Full text only by explicit policy.
```

---

### 4.4 Workspace/project memory

Purpose:

```text
Remember project-specific facts for coding agents.
```

Examples:

```text
repo paths
build commands
test commands
known local conventions
project-specific pitfalls
project-specific tool usage patterns
```

Current repo state:

```text
Blocked. QuantZhai does not currently receive the client cwd, git root, repo
URL, or a stable workspace_id. QZ_ROOT is only the QuantZhai repo root.
```

Allowed readers:

```text
coding profiles operating in the same workspace/project, once workspace_id is
available
```

Default model influence:

```text
Allowed for coding-agent prompts/signals in that workspace.
```

Storage direction:

```text
SQLite for structured facts later; optional generated project note files if
useful.
```

### 4.5 Coding preference memory

Purpose:

```text
Share stable user preferences and coding-agent behaviours across coding
profiles.
```

Examples:

```text
Prefer Devuan/Debian/sysvinit commands.
Use DOCKER_BUILDKIT=1 by default.
Prefer pushd/popd build instructions.
Prefer small targeted patches.
Avoid hallucinated file names.
Treat repo source as truth.
```

Current repo state:

```text
Not implemented. Prompt files, model overrides, and turn harnesses are the
closest current approximation, but they are file-based/profile-scoped, not a
learned preference store.
```

Allowed readers:

```text
coding profile family only, after profile_family exists
```

Default model influence:

```text
Allowed for coding profiles after explicit promotion or trusted config.
```

Storage direction:

```text
Deferred. SQLite typed preferences/skills and generated prompt snippets are
Phase 5+ work, not first DB substrate work.
```

Important:

```text
Do not infer global coding preferences from private/roleplay sessions.
Do not apply coding preferences to roleplay unless a profile explicitly opts in.
```

### 4.6 Profile-private memory

Purpose:

```text
Remember state that belongs only to one profile or persona.
```

Examples:

```text
roleplay continuity
character-specific preferences
private session facts

```

Current repo state:

```text
Not implemented. Profiles carry prompts/overrides/harnesses, but no persistent

```

Allowed readers:

```text
originating profile/session only, unless explicitly exported or promoted
```

Default model influence:

```text
Allowed only for that profile/private scope.
```

Storage direction:

```text
Separate scope rows/tables in SQLite, or separate DB later if a real leak risk

```

Hard rule:

```text
Private/roleplay/intimate facts must never bleed into coding sessions by default.
```


Examples:

```text
curated life artifacts
Holstrom transcripts/indexes
HSM candidate memories

artifact metadata

```

```text
Not implemented. No HSM-specific code, tables, files, or endpoints currently

```

Allowed readers:

```text
HSM/archive profiles and explicit import/export tools only
```

Default model influence:


```text

```

## 5. Scope boundaries

Minimum scope dimensions eventually needed:

```text
tenant_id
  local user/install identity. For now probably one local user.

profile_family
  coding, roleplay, research, hsm, admin, unknown.

profile_id
  Codex-visible profile/model slug or QuantZhai profile identity.

backend_id
  backend GGUF/model identity. Distinct from profile_id.

workspace_id
  repo/worktree/project identity for coding-agent state.

session_id
  client/proxy session id if present or proxy-owned if not.

thread_id
  Codex/OpenAI thread id header if present and captured.

response_chain_id
  chain rooted at first response or previous_response_id lineage.

state_class
  runtime, operational_tool, session, workspace, coding_preference,
  profile_private, hsm_archive, debug_capture.

visibility
  session, profile_private, workspace, profile_family, global_coding,
  hsm_archive, explicit_export, diagnostic_only.
```

Availability notes:

```text
profile_family
  Not represented today. Do not infer from profile names alone. The smallest
  likely change is an explicit profile_family field in model overrides or a
  small profile registry.

workspace_id
  Not derivable proxy-side today. Options: explicit config/env, client-provided
  metadata/header, or deferring workspace-scoped memory until a reliable source
  exists.

session_id / thread_id
  Not consumed today. Capture-audit real local Codex traffic before relying on
  these fields.

previous_response_id
  Not resolved by QuantZhai today. If added, it requires a history/session cache
  and strict scope checks.
```

Default policy:

```text
No cross-scope read unless a policy explicitly allows it.
```

## 6. Bleed-prevention policy

### Forbidden by default

```text
roleplay/private/intimate session state -> coding session
coding project state -> unrelated repo/project
HSM/archive imports -> normal sessions without explicit import
raw captures/logs -> model memory
private profile facts -> global preference store
```

Concrete example:

```text
A roleplay session where the user had sex with a fictional character must not
influence a coding-agent session. It must not become a global user preference,
a coding style hint, or a reusable assistant memory. It belongs to the private
profile/session scope unless the user explicitly exports something from it.
```

Enforcement prerequisite:

```text
The system cannot enforce private/coding separation until profile_family (or an
equivalent explicit privacy class) exists. Add that before storing model-visible
profile-private memory.
```

### Allowed by default

```text
same-session operational tool facts -> same-session convergence signals
same-workspace coding facts -> coding profiles in that workspace, once workspace
  identity exists
global coding preferences -> coding profiles only, after explicit promotion
admin/runtime state -> status/monitor tools
```

### Allowed only after promotion

```text
workspace coding lesson -> global coding skill
session observation -> profile preference
curated artifact -> HSM candidate memory
private/profile fact -> explicit export
```

Promotion must record:

```text
source_scope
target_scope
source_kind
target_kind
reason
created_ts
approved_by_user or approved_by_policy
confidence
redaction_state
```

Promotion is deferred until a preference/skill store exists.

## 7. Storage design

Start with one SQLite DB as the substrate:

```text
var/state/qz-state.sqlite
```

Enable:

```sql
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;
```

Do not start with many DB files. Use one database with strong logical scopes.
Split later only when retention/privacy/lifecycle requires it.

Possible future split:

```text
var/state/qz-runtime.sqlite      runtime/session/tool state
var/state/qz-memory.sqlite       preferences/skills/profile memory
var/state/qz-hsm.sqlite          only if HSM work should live inside QZ
var/cache/qz-cache.sqlite        disposable cache
```

But v1 of this architecture should prefer one DB and strict scope fields.

First DB work must be optional enrichment. QuantZhai must still start and behave
correctly if the DB cannot be opened.


```text

skills
promotion_events

```

Reason:

```text
Those depend on profile_family, workspace_id, promotion semantics, HSM/export
boundaries, and user approval/policy rules that do not exist yet.
```

## 10. Relationship to repeated-read signal

Repeated-read v1 remains scoped and mostly stateless:

```text
seed from visible body["input"]
warn once per run
no persistent session cache
no SQLite dependency
```

Repeated-read v2 depends on this architecture:

```text
query same-scope file_reads/file_writes/signals
handle previous_response_id/minimal-input mode
survive compaction hiding old function_call items
avoid cross-profile/state bleed
```

Do not implement repeated-read v2 until:

```text
profile_family or equivalent privacy class exists
session identity is proxy-owned or captured
workspace_id is available or deliberately omitted from the first scope
cross-scope isolation tests exist
```

Repeated-read v2 must not query roleplay/private/HSM scopes from coding sessions.

## 11. Relationship to HSM and Holstrom work

QuantZhai may become a useful tool for extracting, scoring, and transforming
state for HSM/Holstrom-style projects, but it must not silently become the HSM
store.

Rules:

```text
HSM/Holstrom state requires explicit artifact provenance.
HSM/Holstrom state requires explicit import/export boundaries.
Normal QuantZhai session state is not automatically HSM source material.
Private/roleplay state is not automatically HSM source material.
Coding-agent operational state is not automatically HSM source material.
```

Possible future integration:

```text
QuantZhai can export selected, redacted, source-grounded memories to an HSM
candidate artifact queue.

QuantZhai can query an HSM store through an explicit connector/profile when the
user selects that mode.
```

Do not build that in the first DB layer.

## 15. Acceptance criteria

The architecture groundwork is acceptable when:

```text
1. Every stored fact has memory_class, scope, visibility, and retention policy.
2. Private/roleplay state cannot be read by coding profiles by default.
3. Coding workspace state is shared only inside the same workspace unless
   promoted.
4. Global coding preferences/skills require explicit promotion or trusted config.
5. HSM/Holstrom/archive memory has explicit import/export boundaries.
6. Runtime/admin state can feed monitors/status without becoming model memory.
7. Repeated-read v2 can use same-scope durable read/write/signal facts.
8. previous_response_id/minimal-input support has a clear state lookup path.
9. Compaction-hidden tool history can be represented as structured facts without
   reconstructing private transcripts.
10. Config files, generated Codex catalog files, captures, logs, and benchmark
    artifacts keep their existing contracts until explicitly migrated.
```

## 17. Open questions with current answers

```text
Should profile_family be declared in model overrides, inferred from profile
name, or stored in a separate profile registry?
  Current answer: add explicit profile_family to model overrides first. Do not
  infer from names alone. A separate registry may be useful later but is likely
  overkill for the first pass.

Should private/roleplay memory live in the same SQLite database with hard scope
barriers, or a separate DB file?
  Current answer: same DB with hard scope barriers for v1. Split only if
  concrete retention/privacy/lifecycle evidence demands it.

How does the user approve/promote a learned coding preference?
  Current answer: deferred. Do not design a promotion UI before preferences and
  skills exist.

Can workspace_id be safely derived from git root?
  Current answer: not proxy-side today. The proxy does not see the client's git
  root. It must come from client metadata, explicit config, env, or a later
  protocol addition.

Should HSM/Holstrom integration live inside QuantZhai or as an explicit external
store/connector?
  Current answer: explicit external connector/store boundary first.

How long should operational tool memory live?
  Current answer: session-scoped first; workspace-scoped only after workspace_id
  exists.

How much raw output should be stored versus digests/previews only?
  Current answer: digests/previews for operational memory. Raw output remains in
  capture files unless an explicit storage policy says otherwise.
```
