# Backend Control Plane and Script/Proxy Data-Flow Audit

Date: 2026-05-14
Status: first audit pass. Update as ownership migrates.

---

## Purpose

Map the current llama.cpp/TurboQuant backend control plane and the data flow
between shell scripts, the QuantZhai proxy, runtime state files, and Codex-visible
catalog data. Identify ownership gaps and safe next refactor steps.

This audit was triggered by a live smoke failure where `/health` responded with
`proxy_initialization.ready: false` and `catalog_ready: false`, but `qz-proxy`
had already reported "proxy listening". Codex raced model catalog readiness and
received a 503 "no model available: no match for high".

---

## Non-goals

```text
- Do not rewrite qz-up or replace shell scripts with a daemon.
- Do not change model loading behaviour.
- Do not change memory_domain policy.
- Do not move all control plane logic to the proxy in this pass.
- Do not require backend/model readiness for diagnostic-only proxy routes.
```

---

## Current high-level data flow

```text
User terminal
  -> scripts/qz-up
     -> Docker: starts TurboQuant/llama.cpp container
     -> scripts/qz-proxy: starts Python proxy process
     -> waits for /health (HTTP-only, not catalog/model)
     -> waits for llama.cpp /health (backend process, not model)

scripts/qz-codex
  -> scripts/qz-codex-common: qz_prepare_codex_home()
     -> POST /qz/models/refresh  (or python fallback)
     -> sets CODEX_HOME, CODEX_OSS_BASE_URL
  -> exec codex ...

Codex CLI (as configured)
  -> POST /v1/responses   -> QuantZhai proxy
     -> ProxyLocalToolRegistry: routes to model/backend
     -> normalize_responses_input_for_qwen: history cleanup
     -> normalize_tools_for_llamacpp: tool shape
     -> upstream: http://QZ_SERVER_HOST:QZ_SERVER_PORT/v1/chat/completions etc.
```

## Startup sequence

```text
Step 1  qz-up: Docker run TurboQuant container
Step 2  qz-up: scripts/qz-proxy start (Python proxy background process)
Step 3  qz-proxy: waits for /health to respond (HTTP only)
Step 4  qz-proxy: reports "proxy listening"         ← first "ready" signal
Step 5  qz-up: write_runtime_state --phase proxy-started
Step 6  qz-up: waits for http://QZ_SERVER_HOST:QZ_SERVER_PORT/health  (backend process, not model)
Step 7  (async) Python proxy: initializes model catalog (background)
          -> scans QZ_MODEL_DIR
          -> loads profiles.json / model-overrides.json
          -> writes var/model-inventory.json
          -> loads search policy
          -> sets proxy_initialization.catalog_ready = true
Step 8  qz-up: backend /health responds
Step 9  qz-up: write_runtime_state --phase backend-healthy
Step 10 (deferred) qz-codex: POST /qz/models/refresh (or Python fallback)
          -> proxy regenerates Codex catalog file

Race condition: steps 4–6 can complete before step 7.
Codex requests arriving between steps 4 and 7 receive:
  503: no model available — because catalog_ready is still false.
```

## Readiness sequence (distinct levels)

| Level | Check | Current owner | Visible via |
|---|---|---|---|
| proxy HTTP up | `/health` responds | `qz-proxy` / curl loop | `qz-proxy` stdout |
| proxy fully ready | `.proxy_initialization.ready == true` | Python proxy background init | `/health` body |
| catalog ready | `.proxy_initialization.catalog_ready == true` | Python proxy model scan | `/health` body |
| model visible | `/v1/models` contains the selected model ID | Python proxy catalog | `/v1/models` |
| backend process up | llama.cpp `/health` responds | `qz-up` curl loop | `qz-up` stdout |
| backend model loaded | `/qz/status ready == true` | proxy router | `/qz/status` |

**Gap:** `qz-proxy` only verifies level 1 (HTTP up). `qz-up` verifies level 5
(backend process up). Levels 2-4 are not checked by any script before Codex is
allowed to connect.

## Model identity and Codex catalog flow

```text
var/models/*.gguf files
  -> qz_model_catalog.py: scanned by proxy background init
  -> var/model-inventory.json: written by proxy
  -> Codex-visible model ID = GGUF filename stem (e.g. "kuato")
     OR profile slug if qz.profiles.v1 is configured

Codex catalog:
  var/codex-home/model-catalogs/qwenzhai-models.json
  -> generated by qz_codex_catalog.py (via /qz/models/refresh or Python fallback)
  -> read by Codex at startup from CODEX_HOME

Identity confusion:
  Old aliases (low/medium/high/max/caveman) are REJECTED by scripts/qz-codex.
  Only real /v1/models IDs or qz.profiles.v1 profile slugs are valid.
  Example valid ID: "kuato" (from var/models/kuato.gguf symlink)
  Example INVALID: "high" (was a positional alias, now deprecated)
```

## Current pain points

1. **Readiness gap**: `qz-proxy` reports "proxy listening" when only HTTP is up.
   Catalog and model scans may still be running. Codex can race this and get 503.

2. **Model identity confusion**: old positional aliases (high/medium/low) are
   rejected, but smoke scripts historically used `kuato` as default — which is
   a private local model name. Smokes should default to the first available model
   or require explicit `--model`.

3. **Catalog refresh timing**: `qz-codex-common` calls `/qz/models/refresh` at
   Codex launch, but only after qz-prepare-codex-home completes. If catalog was
   not ready, the refresh re-scans correctly, but there's no explicit wait.

4. **No shared readiness helper**: every script that needs "is the proxy ready?"
   reimplements curl loop fragments.

5. **Missing-model diagnostics**: when a model is not found, the error is just
   "no match for MODEL" with no list of available IDs or alias deprecation hint.

---

## Safe next refactor steps

**Step 1 (done in this pass):** Add `scripts/qz-wait-ready` — a shared readiness
helper that checks proxy/catalog/model readiness with explicit timeout and
actionable diagnostics.

**Step 2 (done in this pass):** Update `scripts/qz-live-smoke` to call
`qz-wait-ready` before running Codex paths, so it fails fast with a clear
readiness error instead of a 503 or model-not-found confusion.

**Step 3 (next):** Improve `scripts/qz-up` to wait for `catalog_ready == true`
before printing "ready". Use `qz-wait-ready --catalog` as the gate.

**Step 4 (future):** Move Codex catalog regeneration entirely into the proxy
`/qz/models/refresh` endpoint. `qz-codex-common` becomes a thin shim that just
calls the endpoint.

**Step 5 (future, SQLite era):** Merge `var/run/*.json` runtime state into
operational facts stored in the Phase 1 SQLite substrate. `qz-write-runtime-state`
becomes a thin shim or disappears.

---

## Open questions

1. **Should `qz-up` gate on catalog_ready?** Currently it only waits for the
   backend process to respond at HTTP. If we wait for catalog_ready in qz-up, the
   startup is slower but safer. Deferred until qz-wait-ready is proven.

2. **What is the right default smoke model?** Using the first available model from
   `/v1/models` is flexible but less predictable. Using an explicit `--model` flag
   is explicit but requires the user to know their model name.

3. **Should proxy_initialization.ready block /v1/responses?** Currently 503 is
   returned when catalog is not ready. This is correct but the error message
   could be clearer.

4. **Is `var/run/qz-runtime-state.json` still needed?** The proxy can now answer
   runtime questions via `/qz/status`. The runtime state file is a startup-phase
   artifact that predates the proxy-owned status endpoint. It can be removed once
   all consumers use `/qz/status` directly.
